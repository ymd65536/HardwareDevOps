# Manufacturing as Code PoC: GitHub Copilot display stand

## Overview

This repository is the first PoC for a manufacturing workflow based on GitHub and OpenSCAD. The aim is to treat a 3D-printed part as a software artifact: source is versioned in Git, regenerated by automation, and validated by rendering to STL and PNG preview.

This PoC focuses on a minimal, parametric display stand for a GitHub Copilot figurine. It intentionally does not modify the official GitHub Copilot 3D model; instead, it creates a separate stand intended to support the figure in a display context.

## Design philosophy

- Represent geometry as source code in OpenSCAD.
- Use named variables for major dimensions instead of magic numbers.
- Keep the design modular through OpenSCAD modules.
- Reserve an extension zone for future fastener or accessory work.
- Prefer reproducibility over visual complexity.

## Model intent

The stand is a compact base with:

- a large support footprint for stability
- a small upper pedestal to hold a figurine
- a top plate for the contact surface
- a reserved name plate zone for labeling
- a dedicated mounting feature module for future screw holes or accessory attachments
- a future mounting area intended for holes or modular inserts

The main parametric inputs are defined in the OpenSCAD source and can be changed by adjusting variables such as stand width, depth, height, and plate thickness. The `mounting_feature()` module keeps the hardware extension isolated and easy to evolve without disturbing the main body geometry.

## Linux-only build pipeline

This repository intentionally uses a pinned Linux toolchain image instead of installing manufacturing tools directly on a developer machine or a generic GitHub runner.

### Canonical local execution

This repository targets `linux/amd64` explicitly. Apple Silicon Macs default to `arm64`, which can produce a mismatched Linux image for the PrusaSlicer toolchain. Use Docker Buildx and set the platform explicitly.

```bash
docker buildx build --platform linux/amd64 --load -t hardware-devops-toolchain:2.9.5 toolchain/

docker pull --platform linux/amd64 ghcr.io/ymd65536/hardware-devops-toolchain:2.9.5

docker run --rm --platform linux/amd64 \
  -v "$PWD:/workspace" \
  -w /workspace \
  ghcr.io/ymd65536/hardware-devops-toolchain:2.9.5 \
  bash scripts/build-model.sh
```

The script is intentionally Linux-only. If it is run outside a Linux environment, it fails fast with a clear message instead of silently depending on host-specific app bundles.

### Repository-managed build contract

The repository build contract is executed inside the container and validates:

- OpenSCAD CLI availability
- PrusaSlicer CLI availability
- required PrusaSlicer profile flags
- parameter validation via `python3 scripts/validate-stand.py`
- STL generation and PNG preview rendering
- G-code export and manufacturing report generation

### What GitHub Actions does

The workflow in `.github/workflows/build-model.yml` performs the following:

1. checks out the repository
2. builds the pinned Ubuntu-based toolchain image
3. logs in to GHCR and publishes the image to the registry
4. validates the toolchain contract inside the image
5. runs the canonical build script inside the container
6. uploads generated artefacts to GitHub Actions
7. exits with a failure if any generation or validation step fails

This creates the core hardware DevOps loop:

```text
Design change
→ Git commit
→ CI build
→ STL generation
→ PNG preview
→ Artifact retention
```

## Current validation status

This PoC validates that the model is syntactically renderable and can be generated in automation. It does not claim that the design is fully print-optimized or physically validated for every printer, material, or figurine shape.

## Known open questions

For now, the repository explicitly records the following unknowns in the design documentation:

- exact figurine footprint and mass tolerance
- printer-specific wall thickness requirements
- infill and orientation assumptions
- acceptable tolerance for future fastening or accessory modules

These items are intentionally left as future improvement candidates rather than guessed assumptions.

## Future Manufacturing as Code directions

The next useful steps would be:

- add automated dimension and geometry sanity checks
- add slicer- or printer-specific manufacturing profiles
- add tolerance and clearance validation
- add a release artifact summary or BOM-like metadata
- add preview diffs and visual review in pull requests

## How to use this repository

1. Clone the repository and open it in a local shell.
2. Ensure OpenSCAD is installed.
3. Run the repository build script:

```bash
./scripts/build-model.sh
```

4. Review the generated files in `artifacts/`:
   - `copilot-stand.stl`
   - `copilot-stand.png`
5. Adjust dimensions by exporting environment variables before the build, for example:

```bash
STAND_WIDTH=100 STAND_DEPTH=80 STAND_HEIGHT=52 ./scripts/build-model.sh
```

6. Commit source changes, push them, and let GitHub Actions regenerate the outputs and store them as artifacts.

This repository is intentionally small, but it establishes the core cycle of design, validation, build, and artifact retention for a hardware PoC.
